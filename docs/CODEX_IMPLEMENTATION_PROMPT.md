# Codex 实施提示词：需求整理与 AI 访谈流程

将下面内容作为 Codex 的任务提示词使用。

---

你要在 `blue7zz/BTaskAssistant` 中实现“需求整理与 AI 访谈流程”。

## 唯一需求来源

按以下优先级读取并执行：

1. 仓库内适用的 `AGENTS.md` / `AGENTS.override.md`。
2. `docs/REQUIREMENT_INTERVIEW_FLOW.md`：本任务的正式产品与流程需求。
3. `docs/SOFTWARE_ARCHITECTURE.md`：技术栈、分层、执行器、存储和安全边界。
4. 当前仓库代码与测试：只用于核验现状，不能反向改写已确认需求。

如果文档之间存在会改变产品行为、公共契约、数据模型或验收标准的冲突，停止并列出冲突，不要自行选择解释。

## 本次执行边界

- 先检查当前分支、工作区和现有实现，不覆盖用户已有修改。
- 只实现用户明确批准的一个阶段；默认阶段为 `docs/REQUIREMENT_INTERVIEW_FLOW.md` 第 15 节的“阶段 1：领域契约与状态机”。
- 如果用户在调用本提示词时明确指定并批准其他阶段，只执行该阶段及其已满足的前置依赖。
- 每完成一个阶段，运行直接相关验证，审计完整 diff，提交实施报告并停止；不得自动进入下一阶段。
- 不重新定义需求，不扩大到资料解析、开发执行、代码审查或自动修复的完整实现。
- 不做无关重构、改名、格式化、依赖升级或“顺便优化”。
- 除非批准阶段明确需要，禁止新增生产依赖、修改公共协议、数据库结构或构建基础设施。
- AI 审批、自动开发和自动完成任务始终属于禁止行为。

## 开始前必须完成

1. 阅读上述文档和适用的仓库规则。
2. 检查 `git status`、当前分支、已有未提交修改和最近提交。
3. 定位当前 Go 领域层、应用层、SQLite、执行器、Wails Bridge 和 React 结构；仓库尚无对应骨架时，只创建当前阶段必需的最小结构。
4. 建立当前阶段的修改清单，说明每个文件对应的需求条目与验证方式。
5. 运行最窄的相关基线检查；若仓库尚无可运行代码，如实记录，不把缺少基线写成通过。

出现以下任一情况时，先停止并请求人工确认：

- 当前实现与正式文档存在重大冲突。
- 必须改变产品行为或验收标准。
- 必须新增生产依赖。
- 必须修改计划外公共 API、协议、数据库或构建基础设施。
- 必须跨越当前获批阶段才能形成可运行结果。
- 预计修改范围明显超过当前阶段。

## 全阶段不变量

实现中必须始终保证：

1. 状态转换由 Go 应用/领域层执行，前端和 AI 不能直接推进状态。
2. AI 只返回候选问题、事实、观察和草稿，永远无权批准。
3. 普通推进与用户强制推进是两条显式路径。
4. 强制推进不会把未回答问题改成已回答；风险和执行停止规则必须保留。
5. 带风险批准需要独立人工动作，结果标记为 `APPROVED_WITH_RISKS`。
6. PI 和 Codex 使用同一执行器能力与内部结果契约，领域层不解析私有协议。
7. 需求分析运行只读，不修改项目、Git、依赖、配置或数据库结构。
8. 输入使用固定上下文快照；项目事实、用户需求和 AI 推断分别存储。
9. 回答、草稿和批准版本追加保存，不覆盖历史。
10. 所有写操作具有状态守卫、幂等语义或乐观锁；前端按钮禁用不能代替后端校验。

## 分阶段执行

### 阶段 1：领域契约与状态机（默认本次范围）

实现：

- `RequirementSessionStatus`、问题级别/状态、需求版本状态、强制推进策略等枚举。
- 会话、问题、回答引用、强制推进记录、需求版本所需的最小领域模型。
- 普通分析、等待回答、AI 建议就绪、强制推进确认、草稿待审查、人工批准和阻塞/恢复转换。
- 普通批准与 `APPROVED_WITH_RISKS` 的守卫。
- 执行器 `requirement-analysis` 能力和统一请求/结果契约；此阶段只定义契约，不接真实进程。
- 纯 Go 单元测试，覆盖每个允许转换以及关键拒绝路径。

验证重点：

- AI 返回就绪后不能直接进入批准状态。
- 存在开放阻塞问题时普通批准失败。
- 未完成逐项策略确认时强制推进失败。
- 强制推进后开放问题仍保留，草稿包含风险与执行规则。
- 带风险批准必须有独立人工确认。
- 非法并发版本和非法状态转换被拒绝。

完成后停止，报告实际文件、测试结果、偏差和下一阶段前置条件。

### 阶段 2：SQLite 与应用服务

仅在用户明确批准阶段 2 后执行。实现文档第 10、11 节的持久化、事务、事件、幂等、乐观锁与应用服务，并以临时 SQLite 完成集成测试。不得接真实 AI 或 UI。

### 阶段 3：统一执行器与 Mock 分析器

仅在用户明确批准阶段 3 后执行。先以确定性 Mock Executor 验证结构化 schema、多轮问答、切换执行器、取消、失败和恢复；不得提前接真实 PI/Codex。

### 阶段 4：Wails Bridge 与 React UI

仅在用户明确批准阶段 4 后执行。实现类型化 Bridge、事件和三栏工作区，使用 `MockAppBridge` 测试交互。前端不得持有审批真相或自行转换状态。

### 阶段 5：PI/Codex 真实适配器

仅在用户明确批准阶段 5 后执行。OMP 必须通过 RPC 接入，不模拟终端；Codex 通过独立适配器接入。两者必须通过相同契约测试和只读权限验证。

### 阶段 6：端到端与稳定性

仅在用户明确批准阶段 6 后执行。覆盖正式文档第 14 节验收标准，特别是人工审批边界、强制推进、恢复、并发冲突、权限和日志脱敏。

## 验证规则

- 每完成一个逻辑单元，运行最窄的格式、静态检查和测试。
- 不删除、跳过或放宽测试来制造通过结果。
- 不声称未执行的命令已经通过。
- 阶段结束时检查完整 diff，确保每个文件都能映射到正式需求。
- 若验证依赖设备、外部 PI/Codex、网络或人工交互，明确区分本地通过与未验证边界。

## 阶段交付

在 `docs/codex-tasks/requirement-interview-flow/` 中生成或更新 `IMPLEMENTATION_REPORT.md`，至少记录：

- 本次批准并完成的阶段。
- 实际修改文件及其需求映射。
- 与文档计划的偏差。
- 执行过的命令及真实结果。
- 未执行验证、原因和剩余风险。
- 需要人工重点审查的 diff。
- 下一阶段的前置条件；不得自动开始下一阶段。

最终回复只汇报本阶段结果并停止，等待人工审查。
